## 4. S2 — synthetic correctness and product acceptance trace

Synthetic scenario tests must cover positive and adverse cases, including:
- A recurring bill candidate can be accepted, corrected, rejected and reconsidered only on material change; review inbox stays quiet for unchanged decisions.
- An **unconfirmed inferred future bill** is excluded from official bill totals/projections, while a source transaction remains visible.
- A potentially overdue signal expresses uncertainty and payment evidence rather than claiming a bill went unpaid.
- Pending-to-posted replacement and linked identity can be simulated without duplicate income/expense; inter-account transfers and card payments cannot be double-counted.

## 5. Architecture candidate and bounded owner burden

**Option A (leading candidate for independent challenge, not adopted):** single-user TypeScript/React web UI with a minimal local Node API, typed provider-neutral domain model, fake-data adapter and a small file/SQLite-like synthetic persistence store. This minimizes compulsory Docker/WSL, separate DB and certificate complexity for the first **development** vertical slice, and can support an on-demand launcher later. Cost could be $0 additional recurring, but actual dependencies, maintenance, security and local storage/backup semantics must be reviewed. Avoid direct browser storage of future Plaid tokens.

**Option B (review alternative):** Next.js/React with a separate PostgreSQL instance through Docker Desktop/WSL2, retaining potential parity with prior Prisma/Postgres proof. More moving parts/volume overhead and Windows Home filesystem/encryption/maintenance uncertainty; could be warranted for later real-data correctness or deployment, but must not be chosen by mere presence of tools. Existing legacy containers/volumes cannot be modified or assumed disposable.

**Option C (minimal frontend-first simulation):** browser-only fixture app for UI prototyping. This may be useful as an early design spike, but **does not meet S1** because durable correction persistence, reliable restart and coherent server-side security/interface boundaries would be unproven. Do not substitute this for functional milestone acceptance.

Builder must compare Option A/B against actual S1 functional requirements and downstream securely separated provider-adapter capability, upfront vs ongoing operating burden, current Windows Home/Node/Docker versions, dependency security/update maintenance, database migration path, and what must be *deferred* until a separately approved host test. No final technology/DB/security choice is owner-approved by this candidate.

**Interface separation:** Accounts, Transactions, SourceSnapshot and UserOverride should have durable stable IDs and explicit source/observed-at/freshness metadata; a read-only mock adapter returns fake source records while an eventual real Plaid adapter has a **separate** token boundary and real-consent gate. Never make a synthetic record look live by silently changing its origin. Versioned schema, deterministic fixtures and tests must demonstrate source/user override reconciliation rather than an in-memory visual simulation.

**Authentication/network boundary:** S1 developer-loopback execution uses only non-sensitive fixture data and must not imply suitability for LAN or real data. A phone-ready or multi-device actual deployment later needs binding/origin rules, HTTPS, private trust, credential/session defenses, physical Windows Home T4 evidence, data encryption and recovery. Never expose a development server to the public internet to meet P10, and never equate a local sample login with real-financial security.
