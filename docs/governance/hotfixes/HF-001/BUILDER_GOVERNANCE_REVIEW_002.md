## Cycle-002 findings

**C02-01 — Roadmap review has contradictory entry/source states (F02).** Section 2 permits entry from *active* `ARCHITECT_NEXT_ITERATION_PREP` or *passive* `AWAITING_OWNER_PATH_DECISION`, but step 1 requires the candidate ref to be created from a verified *passive main D*. Section 1 creates D only after readiness evidence R; it does not define how an active next-prep, potentially before R, reaches that D without either prematurely classifying readiness or leaving an active Architect state on main while another active state is established on the isolated roadmap review ref. Define the exact receipt and state-only relinquishment path from active A to a passive source (and its Handoff/NextRole) before claiming the review ref, or narrow the entry to an already passive D. Test both entry variants, including a crash between relinquishment and ref claim. This is an authority transition, not an editorial detail.

**C02-02 — Roadmap candidate adoption could merge isolated control state into main (F02).** Section 2 places the proposed `docs/PROJECT_ROADMAP.md` and an active `CLERK_PLAN_REVIEW_PREFLIGHT`/later Builder and Creative `.project/CURRENT_STATE.md` on the review ref, then calls for a separate exact-head owner merge authorization to make that candidate accepted on main. A normal merge of that ref into main can bring the isolated review branch's control state, handoffs and review-only candidate into main; the proposed post-merge changed-path check cannot prevent an already published control violation. Define the exact pre-merge reviewed adoption tree/branch and allowed file set, with independent state/roadmap freshness checks and owner authorization bound to the actual merge head. Explain how the accepted roadmap is published without importing isolated role state or treating review approval as implementation/merge approval. A synthetic merge-tree regression should deny the unfiltered review-ref merge.

**C02-03 — Pause create-only ref has an unclassified interrupted phase (F04).** Section 4 P1 first atomically creates `refs/heads/governance/pauses/<PauseID>` at target H, *then* commits and publishes snapshot X. A crash or permission failure after the absent-ref claim but before X leaves an existing pause ref pointing at H with no `PAUSE_SNAPSHOT.md`. The listed replay classifications start with matching X or competing/different X, so this durable created-only state can block idempotent recovery or be mistaken for a conflicting pause. Specify `CLAIMED_NO_SNAPSHOT` recognition by exact ref H, owner decision and target H; allow only guarded completion to X when all original facts remain fresh, else remain PAUSE_PENDING/CONFLICT without deleting or force-moving the ref. Include this phase in HF10/HF11 and never claim WIP preservation or `OWNER_PAUSED` from the ref's existence alone.
