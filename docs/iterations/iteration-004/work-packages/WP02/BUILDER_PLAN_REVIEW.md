## Nonblocking implementation risks within the existing plan

There are **no numbered material change requests**. These are concrete cautions for implementing and verifying the already specified requirements after separate authorization:

1. **Scenario isolation and reset:** `Object.freeze(snapshot)` is shallow, and the valid transaction ID set comes from the canonical fixture. Derive scenario views without mutating nested canonical records or replacing ID validation with only the currently visible subset. A missing/partial scenario must not delete or invalidate saved interpretations. Resetting scenario selection should restore the canonical view with identical override bytes. An arbitrary fixture upload/debug endpoint is unnecessary.
2. **Unknown totals and provenance:** Replace the current null-to-zero total behavior for incomplete scenarios. Independently expected totals and coverage must drive test assertions; copying the UI's own aggregation into the oracle would conceal the defect. The canonical fixture has 245000 + 870000 = 1115000 USD cents and six distinct transactions; partial scenarios must explicitly distinguish a known subtotal from a complete total. Fixture time and simulated freshness must remain visibly synthetic.
3. **Real failure versus browser interception:** Existing F1 covers successful persistence followed by failed refresh; keep its distinct write-confirmed/display-unverified message. Existing F2 reaches the real store's injected rename failure through HTTP. Browser-intercepted PATCH failures alone prove UI feedback, not disk preservation. Retain both layers, prove the failed operation was reached, compare old bytes, and ensure retry does not report an uncommitted edit as saved.
4. **Process and fault harness:** The existing smoke test uses fixed port 4197 and SIGINT shutdown. The expanded journey needs controlled port ownership, bounded startup/exit waits, actual new-process identity, and cleanup restricted to its own children and new directories. Occupied-port and missing-build cases must fail explicitly without killing unrelated services or deleting an existing build/state directory. Corrupt-startup refusal and an in-session read failure are distinct cases.
5. **Accessibility and outbound negatives:** Existing repeated edit-button names and route changes need verifiable context and focus destinations. Test open/cancel/save/failure and filter/retry using the keyboard, including error announcements and focus visibility. Contrast inspection needs recorded values/criteria, not a screenshot-only assertion. Browser request observation should be paired with server/dependency inspection or a controlled server-side negative oracle; browser interception alone cannot certify that Node made no provider request.

These risks are already covered by W1–W5 and their guardrails; they do not require new product decisions or relax the frozen plan. Any material schema, architecture, consent, licensing/security or acceptance change must return through the established owning-role route.
