## Numbered roadmap changes required

### R-01 — Put a documentary Production-path screen before invasive M0 setup

**Location:** Section 4 M0/M1 order; Section 5 first-milestone proof. M0 calls for LAN HTTPS on the Dell and phone, a separate database and backup setup before M1 decides whether the required real Plaid OAuth path is credible under the user's no-domain, home-only and $0/month preferences. The candidate correctly says M0 cannot prove Production, but its ordered path could incur owner trust, firewall, storage and upkeep burdens before checking whether Plaid can plausibly support the first useful release in this topology.

**Required change:** Add a read-only **pre-M0 feasibility gate**: account-specific Trial/allowed-redirect and product information, target-institution OAuth/coverage information that can be obtained without an Item, and a documented viable hypothesis for browser/phone Link plus update-mode repair. Record `UNKNOWN` wherever Plaid will not establish compatibility without a real test. If this screen finds no credible route inside the user's accepted envelope, stop before proposing host setup and return cost/domain/availability alternatives to Architect and user. If it remains plausible but unproven, M0 may proceed only through its later approval and device-consent gates, with Production compatibility still BLOCKED. This does not demand a real Item before M0 or imply one is approved.

### R-02 — Make live database protection and recoverable key custody an M1 entry gate

**Location:** Section 4 M0 exit and M1 dependencies/acceptance; Sections 6–7 security and U-05. M0 requires an encrypted restorable *backup*, and M1 allows a separately consented Production Item with actual balances/transactions. The roadmap mentions live-data encryption as an unknown but does not explicitly require its method and physical proof **before** actual Production records enter the new database. Encrypting tokens and backups alone leaves plaintext financial rows in the live PostgreSQL storage/WSL disk image.

**Required change:** At M0 exit or before any M1 Production connection, require a selected, tested protection boundary for the live database on its actual C:/D: placement; explicit token/backup encryption and key separation; recovery-key custody; least-privilege file/process access; and a synthetic restore that recovers both database and necessary encrypted app state without exposing secrets. Verify the exact Windows Home encryption capability and enabled state instead of assuming BitLocker or Device Encryption. Record a refusal or unavailable protection as BLOCKED for real-data use; handle any new privileged setup through separate informed owner consent. Preserve the legacy Docker volume and existing T7 files.

### R-03 — Define the no-webhook completeness test for every required Plaid state

**Location:** Section 4 M1 acceptance and M2 dependencies; Section 6 data fidelity; Section 7 U-03/U-08/U-09. The roadmap relies on on-launch cursor catch-up and mentions consent/repair, but does not state the proof needed when the Dell is off longer than Plaid's non-Transactions webhook replay window. `/transactions/sync` covers transaction deltas, not all Item, account, balance, consent and product-specific state; first-history completion and actual source freshness also need separate handling.

**Required change:** Add an M1/M2 product-and-state recovery matrix for each required in-scope capability: initial/history completion; added/modified/removed and pending-to-posted transactions; saved-cursor atomicity and pagination restart; account additions/removals; cached balance age versus actual institution refresh; Item errors and update-mode/consent expiration; relevant credit/loan fields; and missed-event behavior after more than seven days offline. State the authoritative poll/status API or user-visible `UNKNOWN` for each, with restart and phone repair evidence. If the no-receiver design cannot recover a required state, mark the affected release outcome BLOCKED and return the availability/network/cost tradeoff to Architect/user. Do not infer fresh data merely because a sync API call succeeded.
